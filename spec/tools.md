# Built-in tools (DRAFT)

A tool is a domain-neutral JSON fragment (entities, state models, actions) that ships with
CEngine and that a template opts into by name. Tools are not templates (ADR-0008): they hold
no roles, prices or trade vocabulary, and the template's own `roles` decide who may use them.

Format (`crates/ce-tools/tools/<name>.json`): `tool`, `version`, `title`, `entities`, and
optionally `actions`. Composition (`ce_tools::compose(template, &["tasks"])`) merges the
fragment into the manifest before validation. It never overrides: a clash with an entity or
action name in the template is an error.

Rules: personal data is marked `pii`; a tool records intent only and never names a provider or
holds credentials (delivery and provider calls are Infajn's); state codes follow the state
registry classes.

First wave in 0.1, status:
- `customers`: `customer`, `customer_contact` (built).
- `tasks`: `task` with open, in_progress, done, cancelled and start/complete/cancel actions (built).
- `notifications`: `notification` records with pending, sent, read, failed; delivery is Infajn's (built).
- `invoicing`: `invoice` (draft, sent, overdue, paid, void) and `invoice_line`, with send/overdue/paid/void actions (built). Totals are derived, never typed in: a line's `line_total` is `round(quantity * unit_price, 2)`, the invoice's `subtotal` is the sum of its lines' totals, and `total` is `subtotal + tax`. The server updates the invoice in the same transaction as any line write. Currency code, non-negative amounts and due date are invariants. No payment collection: that is a payments connector, made through Infajn.
- `audit`: `audit_event`, one row per create, update or delete: entity, record id, operation, actor, request id, time (unix seconds), versions, and the record before and after. The server writes it in the same transaction as the change, so a write that fails leaves no row and a replayed create adds none. Nobody can write it through the API (403); roles that can read it see the trail. The audit entity itself is not audited.
- `changesets`: `changeset` and `changeset_op`. An entity marked `"governed": true` takes writes straight from callers whose role has the `merge_changeset` action; every other caller's create, update or delete is staged and answers 202 with a changeset id. `X-CE-Changeset` adds to the caller's own open changeset. `POST /v1/{inst}/changeset/{id}/{merge|reject|revert|withdraw|preview}`: merge, reject, revert and preview need `merge_changeset`; only the submitter withdraws. `preview` runs the merge in a transaction that is always rolled back and answers `{mergeable, results: [{seq, entity, operation, record}], failure}`, where each `record` is read again at the end (so parent totals, invoice `delta` and `reconciled` are final) `record` is null when a later operation deletes it, and its `id` is null with `id_provisional: true` for a create that did not choose its id (the merge will pick another); `failure` names the first operation that would fail from a rule, lock or changed record (an outage is an error, not a verdict); nothing is kept and the changeset stays open. A merge applies every operation in one transaction with audit, or none; if a record changed since staging the changeset is marked `conflicted`. Revert undoes a merged changeset in reverse order; one that deletes records cannot be reverted (422). The two entities are written by the server only (403).
- `period`: `period` (label, start and end date, `status` open or closed, who closed it and when, a snapshot). `locked_when` is now enforced on every write: an entity that says `ref(period).status == 'closed'` cannot be created in, edited in, moved into or deleted from a closed period (409 `entity_locked`). `POST /v1/{inst}/period/{id}/{close|reopen}` needs the `close_period` action; a close stores how many live records of each entity point at the period. Only these endpoints set the status fields (403 otherwise); both leave audit rows.
- `events`: `outbox_event`. With this tool, every `emit` of an action and every period close or reopen (`period.closed`, `period.reopened`) stores an event in the same transaction as the change, so a rolled-back change leaves none. A relay (`relay_once`, or `POST /v1/{inst}/events/relay` for the caller's tenant) delivers each event as a CloudEvent signed with HMAC-SHA256 through the host's `Deliver` transport (CEngine calls no provider): at least once, in stored order per tenant. A failure backs off 5s, 10s, 20s... up to an hour; the fifth failure dead-letters the event (`last_error` keeps the reason) and later events pass it. `POST /v1/{inst}/events/{id}/replay` puts a delivered or dead-lettered event back in the queue. Both endpoints need the `manage_events` action; the entity is read through the normal list endpoint and written by the server only (403). Events of one transaction are ordered by a nanosecond stamp, so two writers racing in the same instant may swap.
- `bookings`: `resource` and `booking` (requested, confirmed, cancelled, completed, no_show) with confirm/cancel/complete/no-show actions (built). The scheduling logic (recurrence, conflicts, free slots) is `ce-calendar`; wiring it to the server endpoints is still to do.
- barcodes: logic in `ce-barcode` (built).

Invariants (such as a booking's end after its start) are enforced by the server on create and patch (`ce_validate::check_invariants`). Computed fields are evaluated first (`ce_validate::evaluate_computed`: dependency order, decimals rounded half-up to the field's scale), so rules can read them. Rules that use `ref()` or read a computed sum over other records are skipped for now; `unenforced_invariants` lists them.

Second wave: invoicing is built; `ce-io` does CSV import and export (see its crate docs). Search is a list parameter, not an entity tool: mark string or text fields `"searchable": true` and `GET /v1/{inst}/{entity}?q=text` returns the records where any of them contains the text (case-insensitive, 1 to 100 characters, `%` and `_` literal), still tenant-scoped and combinable with `filter`, `sort` and paging. It scans one entity's rows (no full-text index yet); a cross-entity search endpoint comes later.

CSV over HTTP (`ce-io`, any entity): `GET /v1/{inst}/{entity}/_export` returns the entity's records as `text/csv` (needs read access; takes `filter` and `sort` like the list; at most 10,000 rows, otherwise 422 and the caller narrows with `filter`). `POST /v1/{inst}/{entity}/_import` takes a UTF-8 CSV body (at most 1 MiB and 1,000 rows) and needs write access and an `Idempotency-Key`. Every row is checked first; if any row is bad the answer is 422 with a per-row report (`rows`) and nothing is created. Otherwise all rows are created in one transaction through the normal write path (rules, invariants, computed fields, audit, events), so one row the database refuses (a duplicate of a unique field) rolls the whole import back. `?dry_run=true` runs every rule and database check (duplicates, locks, invariants) and rolls back, so it answers what the real import would. Rows are keyed by the key plus a digest of the file, so a retried file replays and a different file never mixes with it. Governed entities refuse imports from callers who cannot merge; server-written entities refuse them always.

Barcodes over HTTP (`ce-barcode`): `GET /v1/{inst}/_barcode?type=code128|ean13|upca|qr&data=...` returns the symbol as `image/svg+xml` (optional `module_size` 1-32, `bar_height` 1-400, `quiet_zone` 0-20). Any caller with a valid token for the installation may use it; it reads and stores nothing. A bad value answers 422 with the position of the first bad character, and a wrong check digit is refused and the right one named. Looking a scanned code up is the ordinary list with a `filter` on an indexed field, so it stays tenant-scoped.

Token issuing (`ce-auth` `Verifier::sign_token`, `ce-server` `Login`): CEngine stores no passwords or PINs. The host gives the server a `Login` (`AppState::with_login(login, tenant, ttl_secs)`), which checks whatever credentials it accepts (a Supabase session, a staff PIN, SSO) and names the caller and their roles. `POST /v1/{inst}/_auth/token` with the credentials as a JSON object (at most 4 KiB, no bearer token) answers `{token, expires_at, roles, sub}`: an HS256 token for the one tenant the host configured (a tenant sent by the caller is ignored), lasting 1 second to 24 hours, carrying only roles the manifest defines. A wrong credential, or a caller left with no defined role, is the same 401 `invalid_credentials`; a lockout answers 429 and an identity service that is down 503 (both retryable); with no login configured the route answers 503. Rate limiting and lockout belong to the `Login` (the server cannot tell a PIN guess from a first try), and any long-lived or refresh scheme is the host's: Platform owns this long term, MJCC uses a small adapter.

Reports (manifest `reports`, any template): a report groups one entity's live records and computes measures over each group. `{"entity": "item", "title": "Stock by category", "group_by": ["category"], "measures": [{"fn": "sum", "field": "value", "as": "total"}, {"fn": "count", "as": "items"}], "filter": "category != 'x'"` (same comparison grammar as a public projection), `"params": ["period"]}`. Functions: `count` (rows, or non-null values of a field), `sum` and `avg` over integer and decimal fields (sums and decimals come back as exact strings, so a total never overflows; a count or integer min and max are numbers), `min` and `max` over integer, decimal, date and datetime. At most 4 group fields (not text, json, file or pii) and 12 measures; groups come back ordered by the group fields with empty values last, at most 1,000 (`meta.truncated`). `GET /v1/{inst}/_report/{name}` needs read access to the entity and answers JSON (`columns`, `rows`), `?format=csv` (spreadsheet-formula guard on text cells) or `?format=html`, a standalone print-ready page with every value escaped, no script, and a policy that forbids loading anything. A declared `param` narrows the report with `?name=value` (equality); `format` is reserved and cannot be a param. Engine-managed state fields can be grouped and filtered. The manifest checker rejects unknown fields, measures over the wrong type, clashing column names and bad filters. Not yet: date bucketing (by month), joins across entities, and totals over `ref` chains.

Free slots over HTTP (`ce-calendar`, needs the `bookings` tool): `GET /v1/{inst}/_slots?resource=<id>&from=<time>&to=<time>&duration=<minutes>[&step=<minutes>]` returns the resource's bookable `{starts_at, ends_at}` slots in time order (at most 1,000; `step` defaults to `duration`). The resource declares `timezone`, optional `buffer_minutes` and `hours`, a JSON object of weekday (`mon`..`sun`) to a list of `["HH:MM","HH:MM"]` local opening ranges; a day with no entry is closed. Requested and confirmed bookings of that resource are busy, recurring ones expanded inside the window, each widened by the buffer; cancelled, completed and no-show bookings are not. Needs read access to `resource` and `booking`. A missing or bad parameter, a window over 366 days, or a resource with no `hours` answers 422 with the path; a resource with more than 2,000 open bookings is refused the same way.

AI data entry (`ce-provider`, any entity): `POST /v1/{inst}/_ai/entry` with `{"entity", "text" (at most 20,000 bytes), "hint" (optional, 500)}` answers `{drafts: [{body, errors}], ready}`: draft records read from the text by the host's AI provider. CEngine never calls a model or holds a key: the server asks its `Provider` (Infajn) for an `ai` connector `records.extract` call, sending only the entity's field shapes (no computed fields) and the text, scoped to the caller's tenant. The answer (`{"records": [...]}`, at most 50) is untrusted: each draft keeps only declared, settable fields, anything dropped is listed on the draft and keeps it out of `ready`, and the rest goes through the same validation as a create. Nothing is saved: the caller shows the drafts to a person and saves them through the ordinary write, batch or import routes, so policy, rules and the audit trail apply as for typed entry. Needs write access to the entity and refuses server-written ones. No provider answers 503, an unreachable one 503 (retryable), and any provider failure 502 with a fixed message (provider text never reaches the caller).
